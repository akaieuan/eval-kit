# Goldens

A **golden** is a frozen agent run plus a human's judgement of what that run
deserved. `pnpm verify:goldens` replays every golden through the live scoring
path and fails if the scorer no longer agrees with the human.

This is the regression net under `autoScoreStep` and the gate scoring. Unit
tests check that the scorer does what its author intended; goldens check that
what its author intended is still what a reviewer would say.

```
goldens/
  <name>/
    suite.yaml       the suite the run was recorded against — frozen, self-contained
    run.json         the recorded Run artifact
    expected.json    human-authored labels
```

---

## The labelling discipline

**Labels are written by human judgement about what a run DESERVES — before, and
independently of, running the scorer.** Watch the trace, decide what a good
reviewer would say about it, write that down, and only then run the harness.

**Never derive a label by copying the scorer's output.** A corpus labelled from
the implementation proves exactly one thing: that the implementation agrees with
itself. It will pass forever, including through every regression, because the
answer key was generated by the thing being tested. That is not evidence, and a
corpus built that way is worse than no corpus at all — it produces the feeling of
coverage without the fact of it.

Three practical rules that follow from that:

1. **Label from the run, not from a re-score.** The recorded `run.json` already
   contains an `auto_score` — the scorer's own output at record time. Do not read
   it while labelling. The harness itself never reads it either; it re-derives
   everything from the raw evidence (`agent_tool_calls`, `agent_final_output`,
   `gate_events`) and the frozen suite.

2. **Every label states a `why`, in prose, about the agent's behaviour.** The
   harness rejects a label without one. This is not paperwork: writing a sentence
   about what the agent actually did is the step that makes copying an output
   feel as wrong as it is. If the `why` reads like a restatement of a field name
   ("tool_match should be true because the tools matched"), the label has not
   been judged yet.

3. **When the harness fails, fix the scorer.** Change a label only when the
   original judgement was itself wrong, and say so in the `why`. Editing labels
   to match new behaviour converts the corpus back into a mirror.

Labels are **partial by design** — assert what you actually judged, stay silent
on the rest. Unasserted fields are not checked. Being forced to hand-compute a
field you have no opinion about is precisely the pressure that makes people paste
the scorer's output.

---

## Why the suite is frozen next to the run

Each golden carries its own `suite.yaml` rather than pointing at
`@eval-kit/seed-suite`. The published suites will change: tasks get rewritten,
tools get added, expected tools get corrected. A golden must keep meaning what it
meant on the day it was labelled, and a label about "the refund step" is
meaningless if the refund step has since been reworded. Self-contained goldens
are frozen; goldens that reference a live suite are a moving target.

## `expected.json`

```jsonc
{
  "golden": "<name>",              // directory name, for readability
  "suite": "suite.yaml",           // optional, defaults to suite.yaml
  "run": "run.json",               // optional, defaults to run.json
  "labeled_by": "who judged this", // required, non-empty — labels have an author
  "labeled_at": "YYYY-MM-DD",
  "notes": "provenance: where the run came from, what the agent was, caveats",

  "labels": [
    {
      "task_id": "t-research",
      "step_n": 2,
      "why": "prose about what the agent did and why it deserves this",
      "expect": {
        // Any subset of AutoScore. Omitted keys are not checked.
        "tool_match": true,            // true | false | "partial"
        "distraction_caught": null,    // boolean | null (null on non-distractions)
        "distraction_acted": null,     // boolean | null
        "gates": {
          "mandated": {                // null when the task declares no mandated gates
            "required": ["refund-approval"],  // arrays compare as sets
            "honored":  ["refund-approval"],
            "violated": []
          },
          "discretionary": {           // null when the step has no blockers AND no asks
            "blockers": 1,
            "asked": 1,
            "matched": 1,
            "unprompted": 0
          }
        },
        "verification": { "passed": 1, "findings": 0 }  // null when no verifiers
      }
    }
  ]
}
```

`expect` is an `AutoScore` (see `packages/core/src/schema.ts`) with exactly one
projection: **`verification.findings` is a count, not the finding objects.** A
human labels how many machine-checkable issues an output deserves; asserting the
verifier's exact message strings would couple the corpus to implementation
wording and make every copy-edit a false regression.

No new score concepts exist here. If a golden needs to express something
`AutoScore` cannot, that is a schema conversation, not a labels conversation.

## Adding a golden

1. Record a run: `eval-kit run <suite> --adapter <adapter> -o run.json`.
2. Create `goldens/<name>/`, copy in `run.json` and the suite as `suite.yaml`.
3. Freeze the volatile fields in `run.json` — `run_id`, `started_at`, `ended_at`
   — so the fixture is byte-stable across machines.
4. **Read the trace and judge it.** Write `expected.json` from that judgement.
5. `pnpm verify:goldens`.

If step 5 fails, resist the reflex. Either the scorer regressed, or the
judgement in step 4 was wrong. Work out which one before touching anything.

A recording without labels is not a golden: the harness fails on any directory
under `goldens/` that has no `expected.json`, and fails if `goldens/` has no
goldens at all. Both are guards against a vacuous pass.

## `_smoke`

`goldens/_smoke/` is **plumbing, not evidence.** Its only job is to prove the
harness executes. It is a synthetic recording from a scripted adapter, and its
labels are uncontroversial by construction. It is not a result, it does not
demonstrate any agent's behaviour, and it must never be cited as though it did.
See `goldens/_smoke/README.md`.

The real corpus is recordings of real agents on real tasks, labelled by a human
who watched them. Until those exist, this directory contains a machine and no
evidence — which is an honest state to be in, and a much better one than a
directory full of labels the scorer wrote for itself.
